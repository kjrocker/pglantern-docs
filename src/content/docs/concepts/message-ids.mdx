A message's durable, public identifier is its `Message-Id` header — the exact
string returned as `message_id` in every message shape, e.g.
`<a1@example.com>`. Routes that address a single message take it not as raw
text but as `:b64id`: the base64url encoding of that string.

```
GET /messages/:b64id
GET /messages/:b64id/thread
GET /messages/:b64id/commits
GET /messages/:b64id/refs
```

## Why not the raw Message-Id in the URL

A `Message-Id` routinely contains `< > @ / % +` — the `<>` wrapper, an `@`, and
occasionally characters that need percent-encoding. Slashes in particular break
path routing: Plug/Phoenix and most proxies reject an encoded `%2F` in a path
segment. Base64url emits none of those characters, so it's a safe path token —
and unlike, say, a `uuidv5` of the Message-Id, it's **reversible**: the server
decodes it straight back to the original string, so no extra indexed lookup
column is needed and a client can build the URL itself from a `message_id` it
already has.

## Encoding convention

Base64url, **unpadded** — `Base.url_encode64(message_id, padding: false)` on
the server, the inverse of `Base.url_decode64(token, padding: false)`. Encode
the `message_id` field exactly as returned by the API, including the `<>`
wrapper.

<Tabs>
<TabItem label="curl">

```sh
MSGID='<a1@example.com>'
B64ID=$(python3 -c "import base64,sys; print(base64.urlsafe_b64encode(sys.argv[1].encode()).rstrip(b'=').decode())" "$MSGID")

curl -s -H "Authorization: Bearer $HORTON_API_KEY" \
  "https://app.pglantern.com/api/v1/messages/$B64ID"
```

</TabItem>
<TabItem label="horton">

```sh
horton messages get '<a1@example.com>'
horton messages thread '<a1@example.com>'
```

`horton` takes the raw Message-Id as printed in any table row (the surrounding
`<>` is fine) or an already-encoded token, and builds the URL for you either
way.

</TabItem>
</Tabs>

## `invalid_message_id`

A `:b64id` path segment that isn't valid base64url, or that decodes to bytes
that aren't valid UTF-8, is rejected with `400`:

```json
{ "error": { "code": "invalid_message_id", "message": "The message-id in the URL is not valid." } }
```

This is a **malformed request target**, not an unknown-entity lookup — it fires
before any database query. A syntactically valid token for a Message-Id that
simply doesn't exist in the archive instead gets `404` (`not_found`).

<Aside type="note">
Message-Ids aren't secret — they're already public in every archived mail
header — so reversibility is a feature, not a leak. Don't try to construct a
`:b64id` by hand from a guessed Message-Id; always encode the exact
`message_id` string a response gave you.
</Aside>

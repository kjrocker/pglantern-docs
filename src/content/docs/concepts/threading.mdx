Every message carries two threading fields, computed by the ingest pipeline
over the full reply graph — never by a client-side `Re:`/subject heuristic:

- **`parent_id`** — the single message this one directly replies to (`null` for
  a thread root). The tree link, derived from `In-Reply-To`/`References`.
- **`thread_id`** — a stable `uuid` shared by every message in the same
  conversation. What `/messages/:b64id/thread` groups on.

`thread_id` is a deterministic hash (`uuidv5`) of the byte-min Message-Id among
the conversation's root nodes — not a sequence, and not assigned in arrival
order. That makes it a pure function of the message set: rebuilding the archive
from the same mail reproduces the same ids, and an ordinary reply landing in an
existing thread never changes that thread's id.

## Fetching a thread

There's no `GET /threads/:thread_id` route. Reach a thread through an anchor
that's independently durable:

```
GET /messages/:b64id/thread   # the thread containing this message
GET /commits/:sha/thread      # the discussion behind a landed commit
GET /threads                  # browse/search threads, newest activity first
```

`/threads` list rows carry a `starter` (the thread's first present message) —
use its `message_id` as the durable handle, not the `thread_id` on the row.

## Why `thread_id` has no route of its own

The reference implementation this archive descends from (pgarchives) assigns
thread ids from a database sequence: a brand-new thread calls
`nextval('threadid_seq')`. That's fine until you need to rebuild the archive
from scratch — sequence values depend on insertion order, so a rebuild produces
different ids than the original run. It's also not what a stable public
identifier should depend on.

Horton derives `thread_id` from message content instead (the root-min
`uuidv5`), which is both append-stable (ordinary replies don't move it) and
rebuild-stable (the same mbox set always yields the same id). The one thing
content-derivation can't avoid: when a later message proves two previously
separate threads were actually one conversation, **two ids can't both survive
the merge**. Horton picks a deterministic winner (the lower root-min) and drops
the loser's row — no alias table, no redirect.

That's the reason `thread_id` was deliberately kept out of the URL space:
v1 has no route that resolves a bare `thread_id`, so a retired id doesn't need
to stay resolvable anywhere. `message_id` is the durable public handle — it
never moves, merge or no merge — and every thread-fetching route anchors on
something equally durable (a message-id or a commit sha). If a `thread_id`
route is ever added, it will need a retired→surviving alias table to keep old
ids resolvable; until then, don't persist a bare `thread_id` as your only
reference to a thread.

<Aside type="tip">
For any link you intend to keep — a bookmark, a stored reference, a join key in
your own data — prefer a message's `message_id` over its `thread_id`.
</Aside>

## `date_estimated`

A thread's flat view (`/messages/:b64id/thread`) is ordered by `sent_at`
ascending. `sent_at` is `NOT NULL`: when a message's `Date` header is missing,
unparseable, or clearly wrong, the pipeline falls back to a `Received`
timestamp and finally, as a last resort, to the first-of-month derived from the
source mbox's filename. `date_estimated` is `true` only when that last,
filename-derived fallback fired — it flags a fabricated-but-plausible
`sent_at` so a client can tell "guessed" from "real" without it being
otherwise indistinguishable. An estimated date is still a real value used for
ordering (never a sentinel like the epoch), so the message sorts among its
actual neighbours in the thread instead of being silently dropped from it.

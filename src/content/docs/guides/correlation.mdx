The archive isn't just messages — it's a graph. A thread argues a change, a patch attachment
carries the diff, a commit lands citing the thread in its `Discussion:` trailer, that commit ships
a GUC or a doc page, and the GUC catalog remembers which major it showed up in. Every edge below is
a real join the pipeline computed once so you don't have to grep commit logs against mbox files by
hand: commit → discussion, message → commits, message → refs, GUC → commit/thread, attachment →
patch, and source path → activity. Chain them and you can go from a `curl` full-text hit to the
exact commit and mailing-list argument that produced it, or from a GUC's default value to the
patch that changed it.

## Commit → discussion

`GET /commits/:sha/thread` takes a full 40-hex sha and returns the threads that argued it — flat,
ordered `sent_at ASC` — plus `unresolved_refs`: `Discussion:` trailer targets that don't resolve to
an ingested message (a phantom link, not an error).

<Tabs>
  <TabItem label="curl">
    ```bash
    curl -s -H "Authorization: Bearer hml_…" \
      "https://app.pglantern.com/api/v1/commits/aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa1/thread"
    ```
  </TabItem>
  <TabItem label="horton">
    ```bash
    horton commits thread aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa1
    ```
  </TabItem>
</Tabs>

```json
{
  "data": {
    "commit": { "sha": "aaaa…1", "subject": "fix btree split bug", "committed_at": "2024-06-10T12:00:00Z" },
    "threads": [
      { "thread_id": "43818d78-a168-46b4-bd0f-02caab97b3e7", "messages": [ /* flat, sent_at ASC */ ] }
    ],
    "unresolved_refs": [
      { "ref_message_id": "ghost@nowhere.example", "source": "trailer" }
    ]
  }
}
```

An abbreviated sha 400s — pass the full 40 hex characters. No commit with that sha is a 404.

## Message → commits

`GET /messages/:b64id/commits` is the reverse edge: given a message, what landed. It walks every
message in the thread, collects commits that cite any of them via a `Discussion:` trailer
(`sources: ["trailer"]`) or a bare sha in a body (`sources: ["body_sha"]`), and groups the result by
commit subject so backpatch siblings (the same fix cherry-picked across stable branches) present
together. An empty `data` array means the thread never landed.

`:b64id` is the unpadded base64url encoding of the exact `Message-Id` — see
[Message-IDs](/concepts/message-ids/) if you're building the URL by hand; the CLI does the encoding
for you from a raw `<message-id>`.

<Tabs>
  <TabItem label="curl">
    ```bash
    curl -s -H "Authorization: Bearer hml_…" \
      "https://app.pglantern.com/api/v1/messages/PGExQGV4YW1wbGUuY29tPg/commits"
    ```
  </TabItem>
  <TabItem label="horton">
    ```bash
    horton messages commits '<a1@example.com>'
    ```
  </TabItem>
</Tabs>

```json
{
  "data": [
    {
      "subject": "fix performance bug",
      "commits": [
        {
          "sha": "aaaa…1",
          "subject": "fix performance bug",
          "sources": ["trailer"],
          "releases": [{ "branch": "REL_16_STABLE", "first_tag": "REL_16_3" }]
        }
      ]
    }
  ]
}
```

`releases` is why this beats grepping `git log`: each commit already carries every stable branch it
shipped on and the first tag that contains it, so "is this fixed in 16.3" is a field, not another
query.

### Message → refs

`GET /messages/:b64id/refs` is the raw material one level down — the code-shaped tokens pipeline
pass 3 pulled out of the message body, before they're resolved into commits: commit shas (with
resolution state), archive message-id URLs, source file paths, CVE ids. Unresolved refs are kept —
a phantom ref (a sha nobody ever pushed, a path that got renamed) is data, not an error.

<Tabs>
  <TabItem label="curl">
    ```bash
    curl -s -H "Authorization: Bearer hml_…" \
      "https://app.pglantern.com/api/v1/messages/PGExQGV4YW1wbGUuY29tPg/refs"
    ```
  </TabItem>
  <TabItem label="horton">
    ```bash
    horton messages refs '<a1@example.com>'
    ```
  </TabItem>
</Tabs>

```json
{
  "data": [
    { "ref_type": "commit_sha", "value": "cccccccccc", "resolved_sha": "cccc…3" },
    {
      "ref_type": "file_path",
      "value": "doc/src/sgml/config.sgml",
      "resolved_sha": null,
      "doc_url": "https://www.postgresql.org/docs/17/runtime-config.html"
    }
  ]
}
```

`doc_url` shows up only for a `file_path` ref under `doc/src/sgml/` that the doc-page registry can
resolve, and it always resolves against the **newest** registry major — a mail body carries no
version identity, unlike a commit (see the next section).

## GUC provenance across versions

`GET /versions/:major/gucs` is the full catalog for one major, name ASC. Add `?changed_since=<major>`
and the response shape switches from catalog to diff — that's the flagship DBA question, "what
changed between 16 and 17," answered in four explicit buckets: `added`, `removed`,
`default_changed` (boot value moved), `context_changed` (the GUC's `context` moved, e.g.
`postmaster` → `sighup`). The latter two carry `from`/`to`; a parameter that moved both its default
and its context appears in both lists.

<Tabs>
  <TabItem label="curl">
    ```bash
    curl -s -H "Authorization: Bearer hml_…" \
      "https://app.pglantern.com/api/v1/versions/17/gucs?changed_since=16"
    ```
  </TabItem>
  <TabItem label="horton">
    ```bash
    horton versions gucs 17 --changed-since 16
    ```
  </TabItem>
</Tabs>

```json
{
  "data": {
    "major": "17",
    "changed_since": "16",
    "added": [
      {
        "name": "io_combine_limit",
        "vartype": "integer",
        "boot_val": "16",
        "context": "user",
        "category": "Resource Usage / Disk",
        "commit": { "sha": "dddd…4", "subject": "Introduce io_combine_limit GUC", "committed_at": "2024-03-01T12:00:00Z" },
        "thread": { "message_id": "<a1@example.com>", "thread_id": "43818d78-a168-46b4-bd0f-02caab97b3e7" }
      }
    ],
    "removed": [],
    "default_changed": [
      { "name": "checkpoint_flush_after", "vartype": "integer", "from": "32", "to": "64", "commit": null, "thread": null }
    ],
    "context_changed": []
  }
}
```

This is the edge that ties the whole graph together in one response: each diff row is decorated
**best-effort** with the newest commit in the target major's branch window whose subject mentions
the parameter (so `commit` can be `null` — a diff row is always emitted even with no cheap subject
match) and, if that commit carries a resolvable `Discussion:` trailer, the `thread` it landed from.
Follow `thread.message_id` into `/messages/:b64id/commits` or `commit.sha` into
`/commits/:sha/thread` to read the actual argument for the default that changed.

<Aside type="caution">
  The diff is only defined between two majors that both have a committed GUC catalog — pass a
  `changed_since` with no catalog and you get `422`, not "everything added." An unknown target
  major (the path segment) is `404` instead.
</Aside>

## Attachment → patch

`GET /attachments/:id/patch` extracts what pipeline pass 3 parsed out of a diff-shaped attachment:
format (`format-patch` / `unified` / `context`), series position (`series_version`/`series_seq`,
read from the filename first and the `[PATCH vN M/K]` subject tag as fallback), the format-patch
subject with the `[PATCH …]` tag stripped, and per-file diffstat, hunk-accurate — not a line count
over the whole attachment, so a patch's commit-message body and its `-- ` mail signature don't
inflate the numbers.

<Tabs>
  <TabItem label="curl">
    ```bash
    curl -s -H "Authorization: Bearer hml_…" \
      "https://app.pglantern.com/api/v1/attachments/1234/patch"
    ```
  </TabItem>
  <TabItem label="horton">
    ```bash
    horton attachments patch 1234
    ```
  </TabItem>
</Tabs>

```json
{
  "data": {
    "attachment_id": 1234,
    "format": "format-patch",
    "series_version": 2,
    "series_seq": 1,
    "subject": "Improve backups",
    "files": [
      { "path": "doc/src/sgml/ref/pg_dump.sgml", "additions": 4, "deletions": 0 },
      { "path": "src/bin/pg_dump/pg_dump.c", "additions": 10, "deletions": 3 }
    ]
  }
}
```

404 covers two cases at once: no attachment with that id, or the attachment exists but isn't a
patch (didn't sniff as a diff in the first 4 KB). There's no "not a patch" marker — a non-patch
attachment simply has no resource here. Check `is_patch` on the attachment's own record if you need
to distinguish "no such id" from "not a patch" up front.

## Source activity

`GET /source/activity?path=<prefix>` is the entry point when you start from source instead of mail
or a commit: everything that touched a tree path, newest first — commits whose file list matches
the prefix, unioned with messages that either attach a patch touching it or cite a file under it in
their body refs. `?major=` narrows the commit arm to that major's containment partition; messages
carry no version identity, so they're unaffected. Bidirectionally keyset-paginated on
`(activity_at DESC, kind, ref)` via `after`/`before`.

<Tabs>
  <TabItem label="curl">
    ```bash
    curl -s -H "Authorization: Bearer hml_…" \
      "https://app.pglantern.com/api/v1/source/activity?path=src/backend/access/&major=16"
    ```
  </TabItem>
  <TabItem label="horton">
    ```bash
    horton activity src/backend/access/ --major 16
    ```
  </TabItem>
</Tabs>

```json
{
  "data": [
    { "kind": "commit", "sha": "aaaa…1", "subject": "fix btree split bug", "activity_at": "2024-06-09T12:00:00Z" },
    { "kind": "message", "message_id": "<b1@example.com>", "subject": "pg_dump patch", "activity_at": "2024-02-01T00:00:00Z" }
  ],
  "next_cursor": "eyJ2IjpbMSwyXSwicyI6Imxhc3QiLCJkIjoiZGVzYyJ9",
  "prev_cursor": null
}
```

From either row you're back on the graph: pull `sha` into `/commits/:sha/thread` for the discussion
behind a commit, or the message's own `/messages/:b64id/commits` and `/messages/:b64id/refs` for
what it cited and where it landed.

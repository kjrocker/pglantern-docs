`GET /search` runs full-text search over message subjects and bodies, then lets you narrow the hit set with the same linkage and metadata filters `/messages` supports.

<Tabs>
<TabItem label="curl">
```sh
curl -H "Authorization: Bearer $HORTON_API_KEY" \
  "https://app.pglantern.com/api/v1/search?q=vacuum"
```
</TabItem>
<TabItem label="horton search">
```sh
horton search vacuum
```
</TabItem>
</Tabs>

`q` is required and must be non-blank — a blank or missing `q` returns `invalid_query` (400). Everything else is optional and composes as `AND`.

## `q` and the `pg` text search config

`q` is matched with `plainto_tsquery('pg', $q)` against a `tsvector` generated from `setweight(subject, 'A') || setweight(body_text, 'D')`. `'pg'` is a custom text search configuration — not the built-in `'english'` — layered on top of Snowball stemming with a domain synonym map and noise filtering:

- **Product-name spellings collapse to one token.** `postgres`, `postgresql`, and `pgsql` all normalize to the same lexeme, so `q=postgres+performance` and `q=postgresql+performance` hit the same messages.
- **pgsql-hackers shorthand expands to the full term.** `autovac` → `autovacuum`, `xact`/`txn` → `transaction`, `idx` → `index`, `func` → `function`, `config` → `configuration` — searching either form matches both.
- **Loanword plurals unify with their singular.** `indices` matches `index`, `matrices` matches `matrix`, `schemata` matches `schema` — a class of Latin/Greek plurals plain Snowball stemming can't reduce.
- **Noise stays out of the index.** Email addresses, URLs, and bare numbers are dropped from the tokenizer's word-token mapping, so they don't contribute to matches or rank.

<Aside type="tip">
The bare token `pg` is deliberately **not** mapped to `postgresql` — the default parser splits identifiers like `pg_dump` and `pg_stat_activity` into a bare `pg` token, so folding it into the product synonym would match nearly every message that references a `pg_*` symbol.
</Aside>

<TabItem label="curl">
```sh
curl -H "Authorization: Bearer $HORTON_API_KEY" \
  "https://app.pglantern.com/api/v1/search?q=indices"
```
</TabItem>

</TabItem>
</Tabs>

## Ranking and the 200-result cap

By default, results are ordered by relevance: `ts_rank_cd(search_vector, plainto_tsquery('pg', $q))` descending, ties broken by `sent_at` and `id` descending. `ts_rank_cd` isn't index-backed — it has to be computed over the candidate rows at query time — so relevance search is capped at **200 results**, full stop. Once you've paged through 200 hits, the next page comes back empty rather than continuing to rank the rest of the corpus.

`sort=sent_at` switches to `(sent_at, id)` descending — an index-backed keyset order with no rank computation and no cap.

<Tabs>
<TabItem label="curl">
```sh
curl -H "Authorization: Bearer $HORTON_API_KEY" \
  "https://app.pglantern.com/api/v1/search?q=vacuum&sort=sent_at"
```
</TabItem>
<TabItem label="horton search">
```sh
horton search vacuum --sort sent_at
```
</TabItem>
</Tabs>

Use relevance (the default) when you want the best few matches for a query — that's what `ts_rank_cd` is for. Use `sort=sent_at` when you need every message that matches `q`, not just the top 200 — an exhaustive pull, a backfill into your own store, or a query broad enough (`q=vacuum` alone can run past 40k matches) that 200 relevance-ranked hits would silently truncate it. Narrowing with `list`, `from`/`to`, or `sender` keeps a relevance search under the cap without giving up ranking.

<Aside type="caution">
The relevance cursor is bound to a hash of `q`. Change `q` between pages, or reuse a relevance `next_cursor` against a different query, and the server returns `invalid_cursor` (400) rather than silently mixing result sets. Relevance search is also forward-only — `prev_cursor` is always `null`. `sort=sent_at` cursors are the ordinary bidirectional keyset cursors described in [Pagination](/concepts/pagination/).
</Aside>

## Linkage filters: committed, path, major

These filter on outcomes recorded against the message's *thread* — whether it landed a commit, what that commit touched, and where it shipped — via `Discussion:` commit-trailer links. They compose with `q` and with each other.

**`committed`** — keep only messages whose thread has (or hasn't) a landed commit:

<Tabs>
<TabItem label="curl">
```sh
curl -H "Authorization: Bearer $HORTON_API_KEY" \
  "https://app.pglantern.com/api/v1/search?q=vacuum&committed=true"
```
</TabItem>
<TabItem label="horton search">
```sh
horton search vacuum --committed
```
</TabItem>
</Tabs>

**`path`** — keep only threads whose landed commit (or an attached patch) touches a file under a source-tree prefix:

<Tabs>
<TabItem label="curl">
```sh
curl -H "Authorization: Bearer $HORTON_API_KEY" \
  --get --data-urlencode "q=vacuum" \
  --data-urlencode "path=src/backend/access/" \
  "https://app.pglantern.com/api/v1/search"
```
</TabItem>
<TabItem label="horton search">
```sh
horton search vacuum --path src/backend/access/
```
</TabItem>
</Tabs>

**`major`** — keep only threads that landed a commit first shipped in a given major branch (`16`, `9.6`, `master`):

<Tabs>
<TabItem label="curl">
```sh
curl -H "Authorization: Bearer $HORTON_API_KEY" \
  "https://app.pglantern.com/api/v1/search?q=vacuum&major=16"
```
</TabItem>
<TabItem label="horton search">
```sh
horton search vacuum --major 16
```
</TabItem>
</Tabs>

A malformed `major` (not a real branch) or a non-boolean `committed` value returns `invalid_params` (422), with the offending field named in the error's `details.param`.

## Metadata filters: sender, from, to

**`sender`** — a case-insensitive substring match against the sender's email *or* display name:

<Tabs>
<TabItem label="curl">
```sh
curl -H "Authorization: Bearer $HORTON_API_KEY" \
  "https://app.pglantern.com/api/v1/search?q=vacuum&sender=alice"
```
</TabItem>
<TabItem label="horton search">
```sh
horton search vacuum --sender alice
```
</TabItem>
</Tabs>

**`from` / `to`** — an ISO-8601 date or datetime bound on `sent_at`. Either can be used alone; both compose into a range. These apply under either sort order:

<Tabs>
<TabItem label="curl">
```sh
curl -H "Authorization: Bearer $HORTON_API_KEY" \
  --get --data-urlencode "q=vacuum" \
  --data-urlencode "from=2024-01-01" \
  --data-urlencode "to=2024-12-31" \
  "https://app.pglantern.com/api/v1/search"
```
</TabItem>
<TabItem label="horton search">
```sh
horton search vacuum --from 2024-01-01 --to 2024-12-31
```
</TabItem>
</Tabs>

<Aside type="note">
`list` (restrict to one mailing list, e.g. `pgsql-hackers`) is also a shipped `/search` query param, matching `/messages`. `horton search` doesn't expose a `--list` flag yet; hit the endpoint directly with `?q=…&list=pgsql-hackers` until it does.
</Aside>

## Errors

- `invalid_query` (400) — `q` is missing or blank.
- `invalid_cursor` (400) — `after`/`before` isn't a valid cursor for this request, including a relevance cursor reused against a different `q`.
- `invalid_params` (422) — a filter value failed validation (bad `major`, non-boolean `committed`, `limit` out of range, both `after` and `before` set). `details.param` names the field.

See [Errors](/concepts/errors/) for the response envelope and the full [error code reference](/policies/errors/).

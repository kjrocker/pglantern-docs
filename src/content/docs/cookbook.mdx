import { Tabs, TabItem, Aside } from '@astrojs/starlight/components';

Each recipe below is a real query against `https://app.pglantern.com/api/v1`, shown as both
`curl` and its `horton` equivalent. Swap in your own paths, shas, and search terms — the shape
of the request is what to copy.

## Every discussion behind commits touching a path

Walk from a source-tree prefix to the commits that touched it, then to the archived thread
behind each one.

<Tabs>
<TabItem label="curl">

```sh
curl -s -H "Authorization: Bearer $HORTON_API_KEY" \
  "https://app.pglantern.com/api/v1/commits?path=src/backend/access/nbtree/&limit=100" \
  | jq -r '.data[].sha' \
  | while read -r sha; do
      curl -s -H "Authorization: Bearer $HORTON_API_KEY" \
        "https://app.pglantern.com/api/v1/commits/$sha/thread"
    done
```

</TabItem>
<TabItem label="horton">

```sh
horton commits --path src/backend/access/nbtree/ --limit 100 --json \
  | jq -r '.data[].sha' \
  | while read -r sha; do horton commits thread "$sha"; done
```

</TabItem>
</Tabs>

`/commits?path=` matches a prefix over touched files, keyset-paginated — page with `after`/
`before` past the first 100. `/commits/:sha/thread` returns the linked archive threads flat,
`sent_at ASC`, plus `unresolved_refs`: `Discussion:` trailers that cite a message-id not found in
the archive (a dead or not-yet-ingested link — surfaced, not hidden).

<Aside type="tip">
For the inverse direction — everything touching a path, commits and patch-carrying messages
together, in one paginated timeline — use `GET /source/activity?path=…` instead. It doesn't
require walking commits first, but it won't hand you the discussion thread for each commit; pair
it with `/commits/:sha/thread` when you find one worth reading.
</Aside>

## Diff a major's GUC catalog with provenance

What changed between two majors, and — best-effort — the commit and thread that changed it.

<Tabs>
<TabItem label="curl">

```sh
curl -s -H "Authorization: Bearer $HORTON_API_KEY" \
  "https://app.pglantern.com/api/v1/versions/17/gucs?changed_since=16"
```

</TabItem>
<TabItem label="horton">

```sh
horton versions gucs 17 --changed-since 16
```

</TabItem>
</Tabs>

The response has four buckets — `added`, `removed`, `default_changed`, `context_changed` — each
entry carrying `commit` and `thread` (both nullable: not every GUC change traces back to an
archived discussion, especially pre-archive or backpatched-without-discussion changes). `major`
and `changed_since` both take a major number, `9.6`, or `master`.

## A sender's patch history

Every patch a sender posted, oldest first, with the parsed diffstat for each.

<Tabs>
<TabItem label="curl">

```sh
curl -s -H "Authorization: Bearer $HORTON_API_KEY" \
  --data-urlencode "q=patch" \
  --data-urlencode "sender=Alvaro Herrera" \
  --data-urlencode "sort=sent_at" \
  -G "https://app.pglantern.com/api/v1/search"
```

</TabItem>
<TabItem label="horton">

```sh
horton search patch --sender "Alvaro Herrera" --sort sent_at
```

</TabItem>
</Tabs>

`sender` is a case-insensitive substring on the display name or email; `sort=sent_at` is what
makes this exhaustive rather than capped at 200. Filter the page to `has_attachment: true`, then
for each hit pull the full message to see which parts are patches:

<Tabs>
<TabItem label="curl">

```sh
B64ID=$(python3 -c "import base64,sys; print(base64.urlsafe_b64encode(sys.argv[1].encode()).rstrip(b'=').decode())" '<msgid@example.com>')
curl -s -H "Authorization: Bearer $HORTON_API_KEY" \
  "https://app.pglantern.com/api/v1/messages/$B64ID" | jq '.data.attachments'

curl -s -H "Authorization: Bearer $HORTON_API_KEY" \
  "https://app.pglantern.com/api/v1/attachments/42/patch"
```

</TabItem>
<TabItem label="horton">

```sh
horton messages get '<msgid@example.com>'
horton attachments patch 42
```

</TabItem>
</Tabs>

`is_patch` on an attachment means it parsed as a diff; only those have a `/patch` resource
(404 otherwise). The patch shape gives `series_version`/`series_seq` (parsed from `vN` filename
or subject-tag conventions) and a per-file diffstat.

## The thread that argued a specific commit

Given a sha you already have, the discussion that produced it.

<Tabs>
<TabItem label="curl">

```sh
curl -s -H "Authorization: Bearer $HORTON_API_KEY" \
  "https://app.pglantern.com/api/v1/commits/aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa1/thread"
```

</TabItem>
<TabItem label="horton">

```sh
horton commits thread aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa1
```

</TabItem>
</Tabs>

The sha must be the full 40-hex form — abbreviated shas get `400 invalid_sha`, never resolved by
prefix match. A commit with no linked thread (a housekeeping commit, or one from before archive
coverage began) returns `threads: []`, not `404`.

## Exhaustive, chronologically-ordered pull of a topic

Every message on a topic, in order, with no 200-result ceiling.

<Tabs>
<TabItem label="curl">

```sh
curl -s -H "Authorization: Bearer $HORTON_API_KEY" \
  "https://app.pglantern.com/api/v1/search?q=incremental+backup&sort=sent_at&limit=100"
# repeat with ?after=<next_cursor> until next_cursor is null
```

</TabItem>
<TabItem label="horton">

```sh
horton search incremental backup --sort sent_at --limit 100
# next: --after <cursor printed to stderr>
```

</TabItem>
</Tabs>

Default relevance order (`ts_rank_cd`) caps out at 200 rows and its cursor is bound to the exact
`q` that produced it. `sort=sent_at` drops both restrictions — it's the index-backed `(sent_at,
id)` ordering used everywhere else, uncapped and reusable. See the [pagination
guide](/concepts/pagination/) for the cursor mechanics.

## Commits landed in a release window

Everything that shipped in a major during a date range — useful for "what landed in the run-up
to feature freeze."

<Tabs>
<TabItem label="curl">

```sh
curl -s -H "Authorization: Bearer $HORTON_API_KEY" \
  "https://app.pglantern.com/api/v1/commits?major=17&from=2024-01-01&to=2024-04-08"
```

</TabItem>
<TabItem label="horton">

```sh
horton commits --major 17 --from 2024-01-01 --to 2024-04-08
```

</TabItem>
</Tabs>

`major` selects the commit's *owning* major — where it first shipped, backpatches included — not
just the branch it was committed to. `from`/`to` bound `committed_at`, ISO-8601 date or datetime.

## A thread's full message list

The entire conversation for a message you already have, flat and in order.

<Tabs>
<TabItem label="curl">

```sh
B64ID=$(python3 -c "import base64,sys; print(base64.urlsafe_b64encode(sys.argv[1].encode()).rstrip(b'=').decode())" '<msgid@example.com>')
curl -s -H "Authorization: Bearer $HORTON_API_KEY" \
  "https://app.pglantern.com/api/v1/messages/$B64ID/thread"
```

</TabItem>
<TabItem label="horton">

```sh
horton messages thread '<msgid@example.com>'
```

</TabItem>
</Tabs>

Ordered `sent_at ASC`, unpaginated — a thread is a bounded conversation, not an open-ended
collection. Any member message-id resolves to the same thread.

## Cross-references extracted from a message

The shas, file paths, message-id URLs, and CVE ids a message's body points to — including the
ones that don't resolve.

<Tabs>
<TabItem label="curl">

```sh
B64ID=$(python3 -c "import base64,sys; print(base64.urlsafe_b64encode(sys.argv[1].encode()).rstrip(b'=').decode())" '<msgid@example.com>')
curl -s -H "Authorization: Bearer $HORTON_API_KEY" \
  "https://app.pglantern.com/api/v1/messages/$B64ID/refs"
```

</TabItem>
<TabItem label="horton">

```sh
horton messages refs '<msgid@example.com>'
```

</TabItem>
</Tabs>

Each ref carries `ref_type` (`commit_sha`, `file_path`, `message_id_url`, `cve`) and, for
`commit_sha`, a `resolved_sha` — `null` means the referenced sha wasn't found in the ingested
commit history, a phantom ref reported as data rather than dropped. A `file_path` under
`doc/src/sgml/` also gets a `doc_url` pointing at the rendered docs page.

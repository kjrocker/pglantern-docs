Every list endpoint (`/messages`, `/search`, `/threads`, `/senders`, `/commits`,
`/attachments`, `/imports`) is keyset-paginated. A page carries `next_cursor` and
`prev_cursor` — opaque strings, either `null` when there's no further page in that direction
— and you hand one back as `?after=` or `?before=`.

All examples assume a key in `$PGLANTERN_KEY`.

## Walk a collection

Page one — newest pgsql-hackers traffic, three at a time:

```sh check=page-one
curl -s -H "Authorization: Bearer $PGLANTERN_KEY" \
  "https://pglantern.com/api/v1/messages?list=pgsql-hackers&limit=3" \
  | jq '{subjects: [.data[].subject], prev_cursor, next_cursor}'
```

```json output=page-one
{
  "subjects": [
    "Re: Planner : anti-join on left joins",
    "Re: Planner : anti-join on left joins",
    "Re: PL/Python initialization cleanup"
  ],
  "prev_cursor": null,
  "next_cursor": "g3QAAAABdwF2bAAAAAJuBwBAQU3sR0cGYgARbnJq"
}
```

`prev_cursor` is `null` — this is the first page. Feed `next_cursor` back as `?after=` for
page two:

```sh check=page-two
curl -s -H "Authorization: Bearer $PGLANTERN_KEY" \
  "https://pglantern.com/api/v1/messages?list=pgsql-hackers&limit=3&after=g3QAAAABdwF2bAAAAAJuBwBAQU3sR0cGYgARbnJq" \
  | jq '{subjects: [.data[].subject], prev_cursor, next_cursor}'
```

```json output=page-two
{
  "subjects": [
    "Create unique GiST indexes",
    "Re: WIP - xmlvalidate implementation from TODO list",
    "Re: Can we remove support for standard_conforming_strings = off yet?"
  ],
  "prev_cursor": "g3QAAAABdwF2bAAAAAJuBwBAVnFeR0cGYgACyJFq",
  "next_cursor": "g3QAAAABdwF2bAAAAAJuBwAArogZREcGYgARbm9q"
}
```

Both cursors are now populated: `?after=next_cursor` continues forward,
`?before=prev_cursor` walks back to page one.

<Aside type="caution">
Cursors are opaque. Don't decode, parse, or construct them — the encoding is an
implementation detail that can change between releases. The only supported operations are
"hand back a cursor you were given" and "compare it to `null`."
</Aside>

## `limit` and the error envelope

`?limit=` bounds the page size: the default is 25, the max is 100. Out of range is
`invalid_params` (422), with the offending field named in `details.param`:

```sh check=limit-error
curl -s -H "Authorization: Bearer $PGLANTERN_KEY" \
  "https://pglantern.com/api/v1/messages?limit=1000"
```

```json output=limit-error
{"error":{"code":"invalid_params","message":"The 'limit' parameter must be an integer between 1 and 100.","details":{"param":"limit"}}}
```

Setting both `after` and `before` on one request is also `invalid_params` (422); a tampered
or truncated cursor is `invalid_cursor` (400):

```sh check=cursor-error
curl -s -H "Authorization: Bearer $PGLANTERN_KEY" \
  "https://pglantern.com/api/v1/messages?after=not-a-cursor"
```

```json output=cursor-error
{"error":{"code":"invalid_cursor","message":"The pagination cursor is not valid."}}
```

## Relevance cursors are query-scoped

`/search`'s default relevance order ranks with `ts_rank_cd`, computed per query — so a
cursor is only meaningful for the exact search that produced it, and the cursor embeds the
query to enforce that.

Take a cursor from one query and replay it against another:

```sh check=cursor-rebind
cursor=$(curl -s -H "Authorization: Bearer $PGLANTERN_KEY" \
  "https://pglantern.com/api/v1/search?q=vacuum&limit=2" | jq -r '.next_cursor')
curl -s -H "Authorization: Bearer $PGLANTERN_KEY" \
  "https://pglantern.com/api/v1/search?q=index&limit=2&after=$cursor"
```

```json output=cursor-rebind
{"error":{"code":"invalid_cursor","message":"The pagination cursor is not valid."}}
```

Relevance paging is also forward-only (`prev_cursor` is always `null`) and capped at 200
results total; `next_cursor` stops appearing at the cap.

## Cursors in the CLI

Paginated `lantern` commands print the next-page cursor to **stderr**, so tables and
`--json` stay pipe-clean, and take it back via `--after`:

```sh check=cli-cursor stderr
lantern messages --list pgsql-hackers --limit 3 >/dev/null
```

```txt output=cli-cursor
# next: --after g3QAAAABdwF2bAAAAAJuBwBAQU3sR0cGYgARbnJq
```

For bulk pulls, `--all` follows `next_cursor` server-side page by page, bounded by `--max`.

```sh check=cli-all
lantern messages --list pgsql-hackers --from 2025-12-29 --all --max 500 --json \
  | jq -s 'map(.data | length) | {pages: length, rows: add}'
```

```json output=cli-all
{
  "pages": 3,
  "rows": 223
}
```

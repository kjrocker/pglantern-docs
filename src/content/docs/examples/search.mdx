`GET /search` runs full-text search over message subjects and bodies. Other filters are
applied on top of the search query to narrow results.

All examples assume a key in `$PGLANTERN_KEY` (see [getting started](/getting-started/));
every output block was captured against the archive as of 2026-01-01.

<Tabs>
<TabItem label="curl">

```sh check=first-curl
curl -s -H "Authorization: Bearer $PGLANTERN_KEY" \
  "https://pglantern.com/api/v1/search?q=incremental+backup&list=pgsql-hackers&limit=3" \
  | jq -r '.data[] | [.sent_at, .sender.display_name, .subject] | @tsv'
```

A blank or missing `q` is `invalid_query` (400), in the standard error envelope:

```sh check=blank-q
curl -s -H "Authorization: Bearer $PGLANTERN_KEY" \
  "https://pglantern.com/api/v1/search?q="
```

```json output=blank-q
{"error":{"code":"invalid_query","message":"A non-blank search query (q) is required."}}
```

## Query syntax

Separate words AND together. A compound identifier is matched as a **phrase**, not as its
parts — searching `pg_monitor` won't drag in every message that happens to mention `pg`
somewhere near `monitoring`:

```sh check=compound
for q in "pg_monitor" "pg monitor"; do
  printf '%-14s' "$q"
  curl -s -H "Authorization: Bearer $PGLANTERN_KEY" \
    --get --data-urlencode "q=$q" --data-urlencode "limit=1" \
    "https://pglantern.com/api/v1/search" | jq -r '"\(.total) \(.total_exact)"'
done
```

```txt output=compound
pg_monitor    431 true
pg monitor    6555 true
```

The gap is the point: `pg_monitor` is one identifier, `pg monitor` is two words that may sit
paragraphs apart. Every `pg_*` name in the archive contributes a bare `pg`, so the loose
form is mostly noise.

Quote a phrase to require the words adjacent and in order:

```sh check=phrase
for q in 'lock contention' '"lock contention"'; do
  printf '%-20s' "$q"
  curl -s -H "Authorization: Bearer $PGLANTERN_KEY" \
    --get --data-urlencode "q=$q" --data-urlencode "limit=1" \
    "https://pglantern.com/api/v1/search" | jq -r '"\(.total) \(.total_exact)"'
done
```

```txt output=phrase
lock contention     7925 true
"lock contention"   1277 true
```

`OR` widens; a leading `-` excludes:

```sh check=operators
for q in 'pg_monitor' 'pg_read_all_stats' 'pg_monitor OR pg_read_all_stats' 'pg_monitor -grant'; do
  printf '%-34s' "$q"
  curl -s -H "Authorization: Bearer $PGLANTERN_KEY" \
    --get --data-urlencode "q=$q" --data-urlencode "limit=1" \
    "https://pglantern.com/api/v1/search" | jq -r '"\(.total) \(.total_exact)"'
done
```

```txt output=operators
pg_monitor                        431 true
pg_read_all_stats                 339 true
pg_monitor OR pg_read_all_stats   667 true
pg_monitor -grant                 141 true
```

Two consequences worth knowing before you script against this: a bare `or` is an operator,
not a word, and a term written `-foo` excludes rather than requires.

From the CLI the query is the positional argument, so phrase quotes have to survive the
shell — wrap them in single quotes:

```sh check=phrase-cli
lantern search '"lock contention"' --limit 1 --json | jq -r '.total'
```

```txt output=phrase-cli
1277
```

Matching is still stemmed inside a phrase: `"pg_monitor"` also matches an adjacent "pg
monitoring". There is no fully literal, case-sensitive mode.

Malformed input is not an error — an unbalanced quote or a lone `-` simply matches nothing.
Only a blank `q` is rejected.

## The `pg` text search config

pgLantern uses a modifed text search configuration that includes domain specific language
and a subset of English irregular plurals, along with filtering of emails and other noise:

- **Product-name spellings collapse to one token** — `postgres`, `postgresql`, and `pgsql`
  normalize to the same lexeme.
- **pgsql-hackers shorthand expands to the full term** — `autovac` → `autovacuum`, `xact` →
  `transaction`, `idx` → `index`.
- **Chosen irregular plurals are handled** — `indices` matches `index`, `matrices` matches
  `matrix`.
- **Noise stays out of the index** — email addresses, URLs, and bare numbers don't
  contribute to matches or rank.

The synonym map is observable from the search totals. Totals above 10,000 are planner
estimates (`total_exact: false`), so compare synonyms on narrower queries where the count is
exact:

```sh check=synonyms
for q in matrices matrix; do
  printf '%-12s' "$q"
  curl -s -H "Authorization: Bearer $PGLANTERN_KEY" \
    "https://pglantern.com/api/v1/search?q=$q&limit=1" | jq -r '"\(.total) \(.total_exact)"'
done
for q in autovac autovacuum; do
  printf '%-12s' "$q"
  curl -s -H "Authorization: Bearer $PGLANTERN_KEY" \
    "https://pglantern.com/api/v1/search?q=$q&from=2025-01-01&limit=1" | jq -r '"\(.total) \(.total_exact)"'
done
```

```txt output=synonyms
matrices    1343 true
matrix      1343 true
autovac     1218 true
autovacuum  1218 true
```

<Aside type="tip">
`pg` is not mapped to `postgresql`, or it would match every `pg_*` prefixed tool from `pg_dump` to `pg_stat_activity`.
</Aside>

## Relevance vs `sort=sent_at`

Default order is relevance (`ts_rank_cd`), with any ties broken by `sent_at`. Relevance
search is **capped at 200 results**, and when more than 2,000 messages match, only the
**2,000 most recent** are ranked — the response's `rank_window` is `2000` then, `null` when
every match was ranked. `sort=sent_at` switches to the ordering by date.

```sh check=relevance-vs-recency
curl -s -H "Authorization: Bearer $PGLANTERN_KEY" \
  "https://pglantern.com/api/v1/search?q=vacuum+truncate&limit=1" \
  | jq '{order: "relevance", total, rank_window, top: .data[0].subject}'
curl -s -H "Authorization: Bearer $PGLANTERN_KEY" \
  "https://pglantern.com/api/v1/search?q=vacuum+truncate&sort=sent_at&limit=1" \
  | jq '{order: "sent_at", total, newest: .data[0].subject}'
```

```json output=relevance-vs-recency
{
  "order": "relevance",
  "total": 5262,
  "rank_window": 2000,
  "top": "[PATCH v5 1/1] Add vacuum_truncate configuration parameter."
}
{
  "order": "sent_at",
  "total": 5262,
  "newest": "Re: How did VACUUM ANALYZE reclaim large TOAST bloat at disk level in\n PostgreSQL 16?"
}
```

Use relevance for "the best few matches"; use `sort=sent_at` for an exhaustive pull — a
backfill, or any query broad enough that 200 ranked hits aren't enough. A windowed match set
ranks recent traffic only: to rank older threads, add `from`/`to` until `total` drops under
2,000 and `rank_window` comes back `null`. The two orders also paginate differently: see
[pagination](/examples/pagination/) for the query-hash binding on relevance cursors.

## Linkage filters: `committed`, `path`, `major`

These filter on outcomes recorded against the message's _thread_ via `Discussion:`
commit-trailer links — whether it landed a commit, what that commit touched, where it first
shipped:

```sh check=linkage-filters
curl -s -H "Authorization: Bearer $PGLANTERN_KEY" \
  --get --data-urlencode "q=vacuum truncate" \
  --data-urlencode "committed=true" \
  --data-urlencode "path=src/backend/commands/" \
  --data-urlencode "major=18" \
  --data-urlencode "limit=3" \
  "https://pglantern.com/api/v1/search" \
  | jq -r '.data[] | [.sent_at, .subject] | @tsv'
```

```txt output=linkage-filters
2025-03-16T00:14:14Z	Re: Disabling vacuum truncate for autovacuum
2025-03-21T15:50:31Z	Re: Disabling vacuum truncate for autovacuum
2025-03-20T21:18:33Z	Re: Disabling vacuum truncate for autovacuum
```

Every hit above sits in a thread that landed a commit, first shipped in 18, touching
`src/backend/commands/`. The same query as a CLI call:

```sh check=linkage-cli
lantern search vacuum truncate --committed --path src/backend/commands/ --major 18 --limit 3 --json \
  | jq -r '.data[].subject'
```

```txt output=linkage-cli
Re: Disabling vacuum truncate for autovacuum
Re: Disabling vacuum truncate for autovacuum
Re: Disabling vacuum truncate for autovacuum
```

A `major` that isn't a real branch, or a non-boolean `committed`, is `invalid_params` (422)
with the offending field named in `details.param`.

## Metadata filters: `sender`, `from`/`to`, `list`

`sender` searches over the sender's email or display name; `from`/`to` are ISO-8601 bounds
on `sent_at`; `list` restricts to one mailing list:

```sh check=metadata-filters
curl -s -H "Authorization: Bearer $PGLANTERN_KEY" \
  --get --data-urlencode "q=vacuum" \
  --data-urlencode "sender=bossart" \
  --data-urlencode "from=2025-01-01" \
  --data-urlencode "to=2025-06-30" \
  --data-urlencode "sort=sent_at" \
  --data-urlencode "limit=3" \
  "https://pglantern.com/api/v1/search" \
  | jq -r '.data[] | [.sent_at, .sender.display_name, .subject] | @tsv'
```

```txt output=metadata-filters
2025-06-27T19:33:30Z	Nathan Bossart	[PATCH v6 1/1] Document pg_get_multixact_members().
2025-06-25T15:21:03Z	Nathan Bossart	Re: Fixes inconsistent behavior in vacuum when it processes multiple\n relations
2025-06-24T18:21:56Z	Nathan Bossart	Re: problems with toast.* reloptions
```

Composing `sender` with `sort=sent_at` is the "one person's history on a topic" recipe —
exhaustive and chronological, not capped at 200.

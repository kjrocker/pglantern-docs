title: Versioning & deprecation
description: What "stable" means for /api/v1 — the breaking-change and deprecation policy.
---

## `/api/v1` is stable

`/api/v1` is the only version that exists and it's stable: response shapes, field names, error
codes, and cursor semantics don't change out from under you. A script written against `/api/v1`
today keeps working.

## What counts as breaking

Anything that would make an existing client's parsing fail or its behavior silently change:

- Removing or renaming a field, endpoint, or query parameter.
- Changing a field's type or meaning (e.g. a timestamp format, a cursor's internal shape).
- Renaming or removing an error `code` (see [error codes](/policies/errors/)) — codes are
  contractual once shipped.
- Tightening validation in a way that turns a previously-`200` request into an error.

## What doesn't

These can land inside `v1`, no version bump:

- New endpoints.
- New optional query parameters.
- New fields in a response body (clients should ignore fields they don't recognize).
- New error `code` values for new failure modes.
- Performance and ranking improvements to search that don't change the response shape.

## Breaking changes ship as a new major

A breaking change means a new version — `/api/v2` — served alongside `/api/v1`, not a mutation of
the existing path. `v1` keeps working during a stated deprecation window (the business default is
six months) before it's turned off. The deprecation announcement states the shutdown date up
front; it isn't a moving target.

There is no `/api/v2` today. Nothing documented here is scheduled to break.
